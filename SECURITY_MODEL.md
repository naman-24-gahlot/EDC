# Security Model

## Core pattern: rules restrict reads, routes own every write
The Firebase Admin SDK bypasses Firestore security rules entirely by design. Rather than
trying to express the full role/state-machine logic in rules (error-prone and hard to
review), this project uses a stricter, simpler pattern:

1. **Firestore rules deny all client-side writes**, full stop. `allow write: if false;` on
   every collection.
2. **Every mutation goes through a Next.js Route Handler.** The handler:
   - verifies the caller's Firebase ID token server-side (`getAuth().verifyIdToken`)
   - reads the role from the token's custom claims — never from the request body
   - checks the action is legal for that role and the current state (see
     [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md) state machine)
   - performs the write via the Admin SDK, writing the matching audit log entry in the same
     operation
3. **Firestore rules scope client-side reads**:
   - `users/{uid}`: readable by the owner, and by any authenticated admin
   - `requests/{requestId}`: readable by the owner (`resource.data.employeeId ==
     request.auth.uid`), and by any authenticated admin. Guards do not read requests
     directly from the client — verification happens server-side in the scan route.
   - `auditLogs/{logId}`: readable only by admins. No client role may write here directly.

This means a review of "can role X do Y" only requires reading the relevant Route Handler,
not reconciling client code against a separate rules file.

## Role resolution
- Role lives in the Firebase custom claim (`role: 'employee' | 'admin' | 'guard'`), set only
  by `scripts/seed-users.ts` (or a future admin-only account-management route) using the
  Admin SDK.
- The `users/{uid}` Firestore doc mirrors the role for display purposes only and is never
  read for authorization decisions.
- A client-supplied role value (in a request body, query param, or form field) is never
  trusted or read.

## Session/auth implementation (Session 2)
- Sign-in happens client-side (`signInWithEmailAndPassword`, Firebase JS SDK). The client
  never stores the ID token — it's exchanged once, immediately, for a session cookie.
- `POST /api/auth/session` verifies the ID token server-side (`adminAuth.verifyIdToken`),
  confirms a valid role claim exists, then issues an **httpOnly, `SameSite=Lax`** session
  cookie via `adminAuth.createSessionCookie` (5-day expiry, `secure` in production).
  `DELETE /api/auth/session` clears it.
- Route protection is done in **server-side layouts**
  (`app/employee/layout.tsx`, `app/admin/layout.tsx`, `app/guard/layout.tsx`), not
  Next.js Middleware/Proxy. Reason: Next.js 16 deprecated `middleware.js` in favor of
  `proxy.js`, and the Admin SDK needs the Node.js runtime rather than the Edge runtime
  Proxy is built around — a server-layout check (`getSessionUser()` in `lib/session.ts`)
  gets the same protection with no runtime mismatch. Every layout calls
  `adminAuth.verifySessionCookie(cookie, /* checkRevoked */ true)`, so a revoked session
  (e.g. an admin deactivating the account) is caught on next navigation, not just at login.
- `lib/firebase/admin.ts` throws immediately if evaluated with `window` defined, as a
  runtime guard against accidental client-bundle import (belt-and-suspenders on top of
  never importing it from a Client Component).

## Firestore rules — deployment
Rules are defined in `firestore.rules` (see repo root) and referenced from `firebase.json`.
They are **not deployed automatically** — deploy manually with:
```
firebase login
firebase use --add        # select this Firebase project once
firebase deploy --only firestore:rules
```

## QR pass token — design (Session 6)

**Format:**
```
token = `${requestId}.${passNonce}.${signature}`
signature = HMAC-SHA256(`${requestId}.${passNonce}`, QR_TOKEN_SECRET) → hex digest
```
`requestId` and `passNonce` (the nonce already generated by the Admin Workflow session's
approve route) contain no `.` characters, so the token splits unambiguously on `.`. The
secret lives only in the server-only `QR_TOKEN_SECRET` env var (already present in
`.env.local` since Session 2/3).

**Deliberately NOT embedded in the token: an expiry timestamp.** Expiry is derived fresh
at verification time from `requests/{requestId}.date` (server-authoritative, set at
request creation — see DATABASE_SCHEMA.md), compared against the *current* server date.
This is simpler than embedding and re-validating a timestamp, and removes any chance of
the token's self-described expiry drifting from the request's actual date. It's also why
the token is **not** independently generated/stored at approval time — it's recomputed
deterministically (same formula, same inputs) wherever it's needed: once when the
employee's pass page renders it, and again inside the verification route to check the
guard's scanned/typed value against it.

**Where it lives:** `lib/qr-token.ts` (server-only, guarded like `lib/firebase/admin.ts`).
This is a deliberate exception to "don't cross-import between employee/admin/guard
folders" — the token *scheme* itself (not UI) is inherently shared between the employee
pass view and the guard verification route, and this session's own brief frames it as one
design covering both sides. Keeping the HMAC logic in one place is what makes "the scheme
stays consistent" true, rather than two independently-maintained copies drifting apart.

**Verification (`POST /api/guard/verify`), in order — first failing check wins:**
1. Split on `.`; require exactly 3 parts (`requestId`, `nonce`, `signature`) → else
   `"Malformed token"`.
2. Recompute expected signature from `requestId`+`nonce`, compare with
   `crypto.timingSafeEqual` (constant-time — a normal `===` on a secret comparison leaks
   timing information an attacker could use to guess it byte-by-byte) → mismatch =
   `"Invalid token signature"`.
3. Look up `requests/{requestId}` → not found = `"Unknown request"`.
4. `status !== 'APPROVED'` → mapped reason: `REVOKED` → `"Access has been revoked"`,
   `CHECKED_IN` → `"Already checked in today"`, `PENDING`/`REJECTED` →
   `"Request not approved"`.
5. `nonce !== request.passNonce` → `"Token no longer valid"` (covers
   approved→revoked→re-approved same day: the new approval issues a fresh nonce, so an old
   QR from the first approval fails here even though a request with that id is APPROVED
   again).
6. `request.date !== todayDateString()` (IST, same helper as Sessions 3/4) →
   `"Pass has expired"`. This is the server-time expiry check — no client- or
   token-supplied timestamp is ever trusted for it.
7. All checks pass → inside a **Firestore transaction**: re-read the request, re-check
   steps 4–6 (closes the race window between the read above and this write), then set
   `status: 'CHECKED_IN'`, `checkedInBy`, `checkedInAt`, and write the `CHECKED_IN` audit
   log entry. Returns `ENTRY APPROVED`.
   The re-check inside the transaction is what makes a concurrent double-scan safe: the
   loser re-reads `status` as already `CHECKED_IN` and falls through to step 4's denial
   instead of double-writing.
8. Any failure (steps 1–6, or the transaction's re-check) writes a `CHECK_IN_DENIED` audit
   entry with the reason in `details`, before returning `NOT APPROVED` — including for
   inputs that don't resolve to a known request or employee at all (see schema note
   below). The manual-entry fallback posts to this exact same route — there's only one
   verification path, not a stricter one for scans and a looser one for typed input.

**Schema note:** `auditLogs.targetEmployeeId` becomes `string | null` (was `string`) —
a malformed or forged token, or one referencing a non-existent request, has no employee to
attribute the denial to. `requestId` was already nullable since Session 4. See
DATABASE_SCHEMA.md.

**Implementation (built same session as this design):** `lib/qr-token.ts` implements
`signPassToken`/`parsePassToken`/`verifyPassSignature` exactly as above.
`app/api/guard/verify/route.ts` implements the 8-step check list verbatim — cheap
pre-transaction reads return specific denial reasons for the common cases, and only the
success path (all pre-checks pass) pays for a transaction, which re-checks everything
before writing. `app/employee/page.tsx` computes the token server-side with
`QRCode.toDataURL()` (the `qrcode` package) whenever `status === 'APPROVED'`, rendering
both the QR image and the raw token text (manual fallback). `app/guard/GuardScanner.tsx`
(client) drives `html5-qrcode`'s `Html5Qrcode` class directly (not its higher-level
`Html5QrcodeScanner` UI) so it can pause on a match, POST to the verify route, show the
result, then auto-resume for the next scan — continuous scanning across multiple
employees without the guard re-opening the camera each time. Also consolidated the
IST-day-boundary helper (previously duplicated in the Employee and Admin sessions) into
`lib/date.ts`, since QR verification made it a third call site — see CLAUDE.md's
context-discipline note on this being past the point duplication is worth tolerating.

**Bug found during the live walkthrough (Session 7):** `html5-qrcode`'s `.stop()` throws
*synchronously* rather than returning a rejected promise when called on a scanner that
never reached a running/paused state (e.g. camera permission denied) — the cleanup
effect's `.catch()` chain never ran, crashing the guard page on switching away from Camera
mode. Not a security issue (verification itself was never affected — this was a UI-layer
crash in `GuardScanner.tsx`), but worth noting since it would have blocked a real guard
mid-shift if the camera failed and this hadn't been caught testing live. Fixed by checking
`scanner.isScanning` before calling `.stop()`, wrapped in try/catch as well.

## Threats explicitly defended against
- **Client-side role spoofing** — impossible by construction; role is never read from
  client input.
- **Cross-employee data read** — Firestore rules scope `requests`/`users` reads to the
  owner or admin only.
- **Token forgery** — requires the HMAC secret, which never leaves the server.
- **Token replay/reuse** — nonce is consumed by the state transition itself, checked inside
  a transaction.
- **Guard or employee reaching admin actions** — every Route Handler checks role from the
  verified token before acting; there is no route that performs an admin action without
  that check.
- **Secrets in the repo** — `.env.local` and any service-account JSON are gitignored;
  `.env.example` lists variable names only.

## What's intentionally out of scope for this prototype
Rate limiting, brute-force login protection, session revocation lists, and multi-factor
auth are not implemented — acceptable for a demo prototype behind Firebase's own default
Auth protections, but should be called out explicitly if this ever moves toward production
use with real personnel data.
